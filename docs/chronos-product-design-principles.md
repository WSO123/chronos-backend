# Chronos Product Design Principles

> 本文沉淀 Chronos 的产品设计原则、产品人格和体验约束。  
> 它用于约束前端体验、后端接口、AI 输出和后续功能取舍。

---

## 1. 产品设计核心

Chronos 的产品设计原则是：

```text
把复杂度藏在背后，
让用户可见的部分尽可能简单但不苍白。
```

无论后续增加什么能力，用户最终都要更强烈地感受到一件事：

```text
Chronos 最擅长的，就是帮我把今天安排成真正做得出来的一天。
```

Chronos 不想成为一个喧闹的效率工具，也不只是一个更聪明的任务列表。

它希望成为一种安静、轻盈、可信赖的存在：

- 把复杂留给系统。
- 把清晰留给用户。
- 让每一天的开始不再被琐碎决策消耗。

真正好的设计不是把一切都摊开，而是把复杂度温柔地藏在背后，让用户看到的部分始终简单、明确、可行动。

Chronos 应该：

- 轻盈，但不轻浮。
- 安静，但不空洞。
- 聪明，但不炫耀。

它不替用户制造压力，而是替用户整理世界，让行动更自然地发生，让专注、节奏与秩序重新回到日常之中。

它不是催促用户更快，而是帮助用户更稳地开始，更清楚地前进。

---

## 2. 产品人格

Chronos 应该像一个轻盈、克制、值得信赖的执行伙伴。

它不喧哗，不施压，不炫耀智能，而是在复杂生活面前提供一种清澈的秩序感，让用户更容易开始，更愿意继续。

产品人格关键词：

- 轻盈
- 克制
- 清澈
- 安静
- 有判断
- 不施压
- 可信赖
- 有节奏感
- 温和但不软弱
- 聪明但不自负

一句话人格：

```text
轻盈但不轻浮，安静但不空洞，聪明而可信。
```

## 3. 核心约束

### 3.1 不要让 Today 变成复杂驾驶舱

Today 是每日执行入口，不是数据大屏。

Today 应该回答：

- 今天先做什么？
- 为什么大概是这个顺序？
- 我现在可以怎么开始？
- 今天进度如何？

Today 不应该默认暴露：

- 复杂评分细节
- 大量洞察图表
- 所有任务历史
- 过多策略配置
- 让用户重新陷入决策的信息

后端对应要求：

- `GET /today` 返回聚合后的轻量视图。
- score factors、完整策略解释、历史变化放到详情接口。
- Today response 以行动序列和当前进度为中心。

### 3.2 不要让 Task Detail 变成信息仓库

Task Detail 是从 AI 决策走向执行的承接层。

Task Detail 应该回答：

- 这是什么任务？
- 它属于哪个目标？
- 为什么现在适合做？
- 下一步怎么开始？
- 有哪些必要步骤？

Task Detail 不应该堆满：

- 所有历史事件
- 所有来源上下文
- 完整 AI 思考链
- 太多依赖图谱
- 复杂长期统计

后端对应要求：

- `GET /tasks/{id}` 只返回执行前需要的信息。
- 任务事件历史通过 `/tasks/{id}/events` 单独获取。
- 来源、依赖、策略解释按需查询。

### 3.3 不要让 Focus 变成控制面板

Focus 是执行场景，不是管理场景。

Focus 应该帮助用户：

- 开始
- 计时
- 勾选步骤
- 完成
- 中断
- 延后

Focus 不应该塞入：

- 大量 AI 洞察
- 复杂统计
- 太多设置
- 让用户继续规划的入口

后端对应要求：

- Focus API 只围绕 session 和行为事件。
- AI 提示最多是轻量建议。
- Focus 操作必须写入 ActivityEvent，用于后续 Report 和学习。

### 3.4 不要让洞察和解释抢走行动感

洞察和解释是为了建立信任，不是为了展示聪明。

默认体验应该是：

- 简短策略摘要
- 必要理由
- 可选择展开
- 用户可修正

不应该是：

- 复杂分析先于行动
- 每个任务都解释过度
- 让用户读完一堆洞察后仍不知道下一步

后端对应要求：

- StrategySnapshot 保存完整策略信息。
- Today 默认只返回 `summary`、`mode`、`primary_reason`。
- 详细 score factors 不默认返回。

### 3.5 不要让“聪明”压过“可信”

Chronos 的 AI 可以有判断，但不能让用户觉得失控。

可信来自：

- 可解释
- 可修改
- 可撤回
- 可追溯
- 不擅自污染正式任务库

后端对应要求：

- AI 输出先进入 schema validation。
- 低置信度或高影响变更进入 Inbox 或等待用户确认。
- 用户对 AI 建议的接受、忽略、修改都要记录。
- AI 不直接无约束写业务表。

## 4. 页面级设计原则

### Today

定位：

```text
决策中心，但不是驾驶舱。
```

体验重点：

- 今日策略摘要
- 推荐执行顺序
- 快速完成 / 延后
- 今日进度
- 轻量风险提示

判断标准：

```text
用户打开 Today 后，是否更容易开始今天？
```

### Task Detail

定位：

```text
行为承接层。
```

体验重点：

- 基本信息
- 所属目标
- AI 建议
- 执行步骤
- Start Focus / 完成 / 延后 / 编辑

判断标准：

```text
用户看完后，是否更清楚下一步怎么做？
```

### Focus

定位：

```text
执行场景。
```

体验重点：

- 当前任务
- 计时
- 步骤勾选
- 完成 / 中断 / 延后
- 极轻量反馈

判断标准：

```text
用户是否更容易保持执行，而不是重新规划？
```

### Report / Me

定位：

```text
反馈与设置收敛。
```

体验重点：

- 完成情况
- Focus 时长
- 延后 / 中断记录
- 简短建议
- 后续优化输入

判断标准：

```text
反馈是否帮助下一轮更好开始，而不是制造压力？
```

## 5. AI 表达原则

AI 的表达应该：

- 简短
- 温和
- 有判断
- 不命令
- 不制造焦虑
- 不过度解释
- 给出下一步行动

避免：

- 夸张语气
- 过度拟人
- 控制欲很强的提醒
- 一次给太多建议
- 把不确定结论说得像事实

推荐表达方向：

```text
今天先从这件开始会比较稳。
这件任务价值高，而且预计耗时不长，适合作为第一个推进点。
```

不推荐表达方向：

```text
你必须立刻完成这个任务，否则今天计划会失败。
```

---

## 6. 工程实现中的设计护栏

后端和 AI 系统在实现时要遵守以下护栏：

- 页面聚合接口默认返回“少而准”的信息。
- 详细解释、历史、来源、评分因子放到详情接口。
- 所有 AI 决策保存摘要和元数据，但不默认展示全部。
- 所有用户修正都写入 ActivityEvent。
- 所有 AI job 都要可查询、可失败、可重试。
- 低置信度 AI 输出不能直接进入正式任务库。
- Focus 相关接口不要混入复杂分析能力。

---

## 7. 一句话原则

```text
Chronos 要把复杂留给系统，
把清晰、节奏和行动感留给用户。
```
